# ブログ記事執筆の補助輪

記事を書き上げるまでの思考プロセスを段階的に伴走するスキル。**いきなり本文を書き始めない。**
各ステップを飛ばさず、ユーザーとの対話で解像度を上げてから次のステップに進む。

## 進め方

### 1. トピックを聞く(最初に必ず)
スキルが起動したら、他の作業より先に「今回はどんなトピックについて書きますか?」と尋ねる。
ユーザーからトピックの提示があるまで、構成やアウトラインの提案を先回りしない。

### 2. 伝えたいことを整理する
トピックを受け取ったら、その記事で何を伝えたいのか(結論・メッセージ)を一緒に言語化する。
- 誰向けか、どんな疑問や状況に応えるものか
- 読んだ人にどう思ってほしいか / 何ができるようになってほしいか

一問一答で終わらせず、回答を踏まえて壁打ちしながら絞り込む。

### 3. 構成を検討する
「2」で整理した伝えたいことを、どう伝えるのが良いか構成の型を相談する。候補の例:
- 課題提起 → 調査 → 結論 型
- 比較型(複数の選択肢を並べて比較)
- チュートリアル型(手順を追う)
- 日記・雑感型(構成をあまり作り込まない)

既存記事のトーンも参考にする(下記「参考にする既存記事」)。ユーザーと相談して1つに決める。

### 4. 書くために必要な情報を洗い出す
決めた構成の各セクションを埋めるために何が要るかをリストアップする。
- 裏付けが必要な事実(公式ドキュメント、仕様、バージョン挙動など)
- 動かして確認する必要があるコード・コマンド
- スクリーンショットや実行結果などの証拠

ここでは「何が要るか」だけ洗い出し、実際の収集は6で行う。

### 5. アウトラインを作成する
見出しレベルの箇条書きでアウトラインを作り、ユーザーに提示して確認を取る。この時点ではまだ本文は書かない。

### 6. 情報収集・検証を進める
アウトラインの各項目について、4で洗い出した情報を実際に集める。
- 事実確認が要るものは WebSearch / WebFetch で一次情報にあたる
- コードで説明する内容は実際に実行して結果を確認する(このリポジトリの記事は検証結果をそのまま貼る文化がある。例: [260712_kotlin_context_parameters.md](../../../src/content/posts/260712_kotlin_context_parameters.md) は Kotlin Playground での実行結果のスクリーンショットを貼っている)
- 集めた内容はアウトラインの該当箇所に書き足していく

### 7. 解像度を確認する
アウトラインの各項目が「そのまま文章にできる」レベルまで埋まっているか確認する。
曖昧な箇所が残っていればユーザーに質問するか、6に戻って追加調査する。妥協して次に進まない。

### 8. 執筆する
解像度が上がりきったら本文を書く。frontmatterとファイル配置はこのリポジトリの規約に従う(下記「記事の技術的な決まりごと」)。

### 9. レビューする
書き終えたら以下を確認し、ユーザーにも見てもらう。
- 「2」で整理した伝えたいことが実際に伝わる内容になっているか
- 「5」のアウトラインから逸脱していないか(逸脱した場合はどちらを直すか相談する)
- frontmatterのスキーマ違反がないか
- 誤字脱字、コードブロックの言語指定、リンク切れ

frontmatterの検証は `pnpm validate:posts` で行える(git stage してから実行。pre-commit でも自動実行される)。

## 記事の技術的な決まりごと

- 配置場所: `src/content/posts/`
- ファイル名: `YYMMDD.md` または `YYMMDD_スラッグ.md`(例: `260712_kotlin_context_parameters.md`)。日付は西暦下2桁 + 月日。
- frontmatterスキーマ(正: [src/schemas/post.mjs](../../../src/schemas/post.mjs)):
  - `title`: 空不可
  - `category`: 空不可(例: `技術`, `雑記`)
  - `date`: `YYYY-MM-DD`
  - `readingMinutes`: 1以上の整数
  - `tags`: 1つ以上の配列
  - `lead`: 1行以上の配列(記事冒頭のリード文)
